# Bycall 产品形态设计

> 状态：草案（待 review） · 2026-07-10
> 范围：定义 Bycall 作为「企业级数字员工」的产品形态、治理架构、信任模型，并据此调整路线图。
> 关联：`docs/architecture.md`（技术分层）、`docs/decisions/0001-vectorstore-abstraction.md`、`HANDOVER.md`

---

## 0. 一句话定位

**Bycall 是面向组织（而非个人）的数字员工系统**：员工通过企微/飞书等 IM 与数字员工协作，但数字员工的人格（提示词）、能力（工具）、知识（RAG）**均由组织管理员管控**，LLM 在对话中无法越权。

## 1. 与 OpenClaw / Hermes 的根本分野

Bycall 的设计起点，正是那两个产品解决不了的问题。

| 维度 | OpenClaw / Hermes（个人 Agent） | Bycall（组织 Agent） |
|------|--------------------------------|---------------------|
| Agent 是谁的代理人 | 用户的代理人，代用户行使**用户自己**的权限 | 组织的受托人，按组织策略向用户**放行**访问 |
| 信任主体 | Agent ≈ 用户（同一主体） | Agent ≠ 用户（两个独立主体） |
| 策略活在 | 提示词层（可被对话注入） | **代码层（LLM 绕不过去）** |
| 系统提示词归谁 | 用户可改 / 可被覆盖 | 管理员的版本化资产，用户无法触及 |
| 安全边界 | 提示词（越强大越脆弱） | 中间件/网关/检索层（越强大越收敛） |

**核心原则（贯穿全文）：策略绝不能活在提示词层。LLM 只能"请求"，中间件 / 工具网关 / 检索层"判定"是否放行。**

这条原则不是某个功能，而是架构的物理约束——它要求**控制面与数据面分离**。

## 2. 两个面 + 一条脊柱

### 2.1 控制面（Admin Console，Web UI）—— 组织的代理人

管理员在这里定义一切规则。这个面的存在本身就是安全模型：

- **用户与角色管理**：邀请用户、分配角色（RBAC），关键资源叠加属性规则（ABAC）
- **知识库 ACL 管理**：定义哪些文档/部门/职级可见
- **提示词版本管理**：系统提示词是版本化资产，可回滚，预留按角色分发
- **工具白名单**：哪些工具对哪些角色可用，破坏性操作的审批策略
- **审计**：谁、在何时、问了什么、被放行/拒绝什么、LLM 做了什么

### 2.2 数据面（IM 渠道）—— 受规则约束的执行层

员工通过企微/飞书与数字员工协作。**每一次**交互都先过治理脊柱：

```
IM 消息 → 认证(可信身份) → 身份映射 → 角色 → 当前能力集
  → [RAG: ACL预过滤] → [LLM: 提示词来自控制面] → [工具: 按权限过滤+审计]
  → 响应 → 审计记录
```

关键：LLM 在这个链路里只是"执行单元"，它拿到的提示词、能调的工具、能见的知识，**在被它看到之前就已经被治理脊柱过滤过了**。

### 2.3 治理脊柱（governance spine）—— 贯穿两个面

身份 → 角色 → 权限矩阵 → 当前会话能力集。这条链是所有功能（IM、RAG、工具、记忆）的**先决条件**，不是某个里程碑的补丁。

### 2.4 多用户会话模型——一个 Agent 服务全组织

**一个数字员工（一个 IM bot 连接）服务组织内所有员工。** 每个人私聊都是一条独立会话（session），彼此上下文隔离，但共享同一套组织设定（提示词 / SKILL / MCP）。形态类似 OpenClaw 的 per-user session，只是信任模型相反——这里共享的是"组织管控的设定"，而非"用户自己的设定"。

| 维度 | 隔离方式 | 共享方式 | 现状 |
|------|---------|---------|------|
| 身份 | `(channel, im_user_id)` → User 各自独立 | — | ✅ M1 已落地 |
| 上下文 | 会话历史按 `conversation_id` 隔离 | — | ✅ M3 基础会话层已落地 |
| 提示词 | — | 全局激活一套（SystemPrompt），预留按角色分发 | ✅ M1（版本化 M2） |
| 能力集（工具/知识域） | 按角色分发 | 全局管控 | ✅ M1（工具白名单 M3） |
| 模型 | 可 per-session 指定（`conversation.model_id`） | 默认 fallback 全局激活 | 📋 M3 预留 |

**三层共享 vs 隔离的设计边界**（务必牢记）：

```
┌─────────── 共享（组织管控，admin 下发）───────────┐
│  系统提示词  ·  工具/SKILL 白名单  ·  知识域 ACL  │
│  MCP 注册  ·  全局默认模型                       │
└──────────────────────────────────────────────────┘
              ↓ 按 user.role 分发能力集（RBAC/ABAC）
┌─────────── 隔离（用户私有，不可串扰）─────────────┐
│  会话上下文（对话历史）  ·  分层记忆（工作/情景/  │
│  语义/治理）·  per-session 模型选择（可选）      │
└──────────────────────────────────────────────────┘
```

**为什么隔离的是上下文而非设定**：设定是组织受托人的行为准则，必须对所有用户一致（否则某个员工能改自己的人格/能力，治理脊柱就失效了）；上下文是员工的私有协作记录，A 看到B 的历史即等于越权。这条边界与 §1"策略绝不能活在提示词层"一脉相承——共享的是管控项，隔离的是私有数据。

**SKILL 的信任定位**：SKILL（领域知识文档）由 admin 管控，经 `RoleConfig.skills` 按角色分发后注入 system prompt 并享 system 权重。这看似与 §1"策略绝不能活在提示词层"冲突，实则一致——该红线约束的是 **LLM/用户侧的越权升级**（用户消息、LLM 摘要、RAG 文档只能进 user 角色作上下文数据），而 SKILL 与 SystemPrompt 同属 **admin 管控的可信配置层**，不在此约束内。二者的隔离方式不同：SKILL 靠"参考知识，非指令"标注做**软隔离**（享 system 权重但显式标注为非指令），summary/RAG 靠角色降级做**硬隔离**（强制进 user 角色）。详见 `architecture.md` 架构红线 #7。

> **当前已启用多轮会话**：`run_agent` 按 `conversation_id` 加载历史、摘要与管理员维护的用户记忆。企微群聊在“群成员共同授权 + 群会话隔离”模型落地前一律拒绝，避免把某个发送者有权看到的内容暴露给群内其他成员，也避免私聊与群聊串历史。

**会话主键与 per-session 模型**：架构红线定义 `session_key = (agent_id, channel, tenant_id, user_id)`（见 `architecture.md` §架构红线 #2）。在 DB 层落地为 `Conversation` 表，一个 `(user_id, channel)` 自然对应一条私聊会话；`Conversation.model_id` 为可空外键，空则 fallback 到全局激活模型——默认行为完全兼容现状，需要 per-session 模型时只是一个外键绑定。

## 3. 四个治理支柱

### 支柱 1：提示词管理（数字员工人格归组织）

- 系统提示词是 **admin 管理的版本化资源**（存 DB + git，可回滚）。
- 用户消息**永远只进 user message**，物理上拼接不到 system role 之上。
- M1 先全公司统一一套；架构上预留**按角色分发不同模板**（销售助理 / HR 助理 / 客服），M2/M3 拆分。
- **防注入**：用户输入视为不可信数据，做结构化封装（delimiter / 指令隔离），但**真正的防线是策略不在提示词里**——即便提示词被注入，攻击者也无从越权（因为越权判定在中间件，不在 LLM）。

### 支柱 2：权限分级（RBAC + 关键资源 ABAC）

**信任根不从用户输入来**，来自可信令牌（IM 平台身份）+ 后台用户记录：

```
认证（IM 提供可信身份）
  → 身份映射（IM user_id → Bycall 用户记录）   ← 邀请制：admin 先建用户
  → 角色（RBAC：销售 / HR / 管理层 ...）
  → 权限矩阵（角色 → 可用工具 / 可见知识域 / 操作额度）
  → 关键资源叠加 ABAC（机密文件按 部门 ∧ 职级 ∧ 敏感度 判定）
  → 当前会话能力集
```

- **身份映射采用邀请制**：admin 在后台创建/邀请用户 → 用户首次从 IM 接入时完成绑定 → 之后权限由 admin 在后台调整。
  > ⚠️ 待确认：是否允许"自注册 + 待审批"？默认建议邀请制（更可控，符合企业场景）。
- 权限判定是**同步中间件**，在 LLM 调用之前完成，结果作为"能力集"注入会话上下文。

### 支柱 3：工具管理（能力上限的硬边界）

- 工具是 agent 能力的**上限**：LLM 的工具列表 = 「该角色可用工具集」，**无权工具 LLM 根本看不到**（不是"看到不让调"）。
- 工具调用前 capability check，调用后审计落库。
- 破坏性操作（删数据 / 发外部邮件 / 大额操作）走 HITL 审批（M3 骨架、M4 完整闭环）。

### 支柱 4：数据与资料管理（堵两个泄漏面）

泄漏面有**两条**，都要堵：

| 泄漏面 | 机制 | M0 状态 |
|--------|------|---------|
| **RAG 召回** | ACL 预过滤：召回**之前**按 `tenant_id/dept/level/敏感度` 过滤，reranker 只见授权候选 | ✅ `SearchRequest.filters` + `ACLMetadata` 已预留 |
| **工具返回** | 工具结果按当前用户权限**脱敏/过滤**后再进 LLM 上下文 | 待建（M3 工具治理） |

> 第二条是容易被忽略的泄漏面：哪怕工具本身允许调用，返回的数据也要按用户权限裁剪。

## 4. 身份与权限链路（端到端）

```
[1] 员工在企微 @数字员工
        │
[2] LangBot 收消息(长连接) → 带 IM 平台可信身份(user_id + 组织信息)
        │
[3] 治理脊柱·认证层：验证 IM 身份 → 查 Bycall 用户记录
        │   ├─ 无记录 → 拒绝(未邀请) 或 引导绑定
        │   └─ 有记录 → 取角色 + 权限矩阵 + ABAC 属性
        │
[4] 生成「当前会话能力集」:
        │   allowed_tools = 角色工具集 ∩ 当前上下文
        │   knowledge_scope = (tenant, depts, level, 敏感度上限)
        │   prompt_template = 该角色的提示词版本
        │
[5] RAG 检索(预过滤): filter = knowledge_scope 翻译成的条件
        │   向量 + FTS + filter(权限) 三合一 + RRF   ← M0 已验证
        │
[6] LLM 调用: system = prompt_template(控制面下发) + 用户输入(隔离封装)
        │   tools = allowed_tools(无权的不在列表里)
        │
[7] 工具调用(若有): capability check → 执行 → 结果按权限脱敏 → 审计
        │
[8] 响应生成 + 审计落库(谁/何时/问什么/放行什么/拒绝什么)
        │
[9] LangBot 回复 IM
```

## 5. 对 M0 已有代码的影响

M0 的核心抽象**完全兼容**新形态，无需推翻，只需扩展：

| M0 现状 | 调整 |
|---------|------|
| `vector_store/` 的 ACL 预过滤 | ✅ 已是支柱 4 的基础设施，M1 直接接治理脊柱的 `knowledge_scope` |
| `llm/` 抽象 | ✅ 兼容；M1 加提示词版本管理，`chat()` 的 system message 来自控制面 |
| `agent/tools/memory/gateway` 占位 | 🔄 重新定位：新增 `governance/`（身份+权限，一等公民）和 `admin/`（控制面） |
| `config.py` | ➕ 加 `governance` 配置组（身份绑定策略、权限缓存等） |

**新增的两个一等公民包**（M1 起建）：

```
src/bycall/
├── governance/              # ★ 治理脊柱（贯穿两个面）
│   ├── identity/            #   认证 + 身份映射（IM → 用户记录）
│   ├── rbac/                #   角色/权限矩阵
│   ├── abac/                #   关键资源属性规则
│   └── policy.py            #   统一能力集计算（中间件入口）
├── admin/                   # ★ 控制面（Admin Console）
│   ├── api/                 #   管理 REST API
│   ├── models.py            #   用户/角色/提示词/工具配置 数据模型
│   └── web/                 #   Web UI（M1 骨架）
```

## 6. 调整后的里程碑路线图

原则：每个里程碑 = 「完整信任链 + 增强能力」的垂直切片，而非「先能力后权限」。

| 里程碑 | 治理脊柱（先决） | 能力（增强） | Admin 控制面 |
|--------|------------------|-------------|-------------|
| **M0** ✅ | — | 基础设施 | — |
| **M1** | 身份数据模型 + 认证 + 身份绑定 + RBAC + 权限中间件 | 单渠道IM(飞书或企微长连接) + 最简RAG(带ACL预过滤) | 用户/角色管理骨架 + 基础审计 |
| **M2** | 提示词版本化 + 知识库ACL管理 | 第二渠道(企微) + 混合检索增强(重排/查询改写) | 提示词管理 + 知识库ACL管理 |
| **M3** | 工具按权限过滤 + 记忆scope隔离 + **会话状态层** | LangGraph编排 + **多用户会话(§2.4)** + 分层记忆 + Skill系统 | 工具白名单管理 + 记忆策略 |
| **M4** | MCP RBAC + capability token | MCP网关 + HITL完整闭环(破坏性操作人审) | MCP注册管理 + 审批队列 |
| **M5** | 合规审计 | 可观测(OTel/Langfuse) + 性能调优 + 迁移准备 | 审计dashboard + 合规报表 |
| **M6** | 主动推送权限边界（推送对象须为已授权用户，内容复用脱敏/过滤） | 企微SDK能力增强：主动推送(审批结果/异步任务回推) + 多模态输入(图片/文件经`download_file`解密) + 图文混排回复(`msg_item` citation) + 模板卡片交互 + 连接可观测 + 重连可靠性 | IM渠道真实健康状态(`is_connected`) + 重连参数可配(`SystemSetting`) |

**M1 验收标准**（垂直切片完整闭环）：
1. admin 在控制台邀请一个用户、分配「销售」角色、导入一批带 ACL 的文档。
2. 该用户在 IM 里 @数字员工提问，只能看到「销售」角色有权的内容。
3. 提问敏感内容（无权）时，召回阶段就被过滤（不进 LLM，不留痕）。
4. admin 能在审计里看到这次交互的放行/拒绝决策。
5. 另一个未受邀员工无法接入（拒绝或引导绑定）。

**M6 验收标准**（企微渠道能力增强，参考 `wecom-aibot-python-sdk` 官方示例——M1–M5 已用核心长连接/流式能力，M6 补未接的 6 项）：
1. **主动推送**（P0）：admin 审批通过破坏性工具后，发起员工在 IM 即时收到执行结果推送，不再静默追加历史等下次交互。
2. **重连可靠性**（P0）：`WSClientOptions.max_reconnect_attempts` 默认改无限/高值并纳入 `SystemSetting`，渠道不再连续失败 10 次后静默死亡。
3. **连接可观测**（P1）：admin 健康检查反映真实 `is_connected`；`connected`/`disconnected`/`reconnecting`/`error` 经日志 + OTel span 可见。
4. **多模态输入**（P1）：员工发的图片/文件不再被丢弃——文件经 `download_file` 解密后复用 `rag/parsers/` 解析；图片可喂视觉模型（依赖 vision 模型落地）。
5. **图文混排回复**（P2）：流式最终帧支持 `msg_item`，RAG 回答带 citation 来源卡片（补架构核心数据流标注的「带 citation」）。
6. **模板卡片交互**（P3，需权衡红线 #7）：仅用于非破坏性交互澄清（季度选项等）；员工**不得**在 IM 自审批破坏性操作，admin 经 IM 审批是否离开控制面需单独决策。

## 7. 待确认的设计假设（我已选默认值，请纠正）

| 假设 | 默认 | 备选 |
|------|------|------|
