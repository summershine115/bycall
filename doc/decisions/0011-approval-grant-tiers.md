# ADR-0011：审批授权三档（once/session/always）持久化与撤销

- **状态**：✅ 已采纳
- **日期**：2026-08-21
- **背景**：T3.3 高风险 HITL 审批链——M4 的审批门对每次破坏性工具调用都创建
  pending 请求，高频可信操作（如值班期内的工单回写）会淹没管理员，管理员被迫
  批量放行反而稀释了人审价值；同时「授权后免审」缺少组织可控的档位与撤销路径。
- **关联**：ADR-0002（graph 无状态 + session_store 管会话）、execution-plan T3.3、
  `doc/architecture.md` 红线 #5（破坏性操作走人审）、M4 Slice C 审批门

## 决策

批准一条审批时可选授权档位，**持久化在独立 `ApprovalGrant` 表**（而非提示词或
内存）：

1. **三档语义**：
   - `once`（默认）：仅本次执行，不落授权表——既有语义，零新增风险；
   - `session`：绑定发起 `conversation_id`，该会话内同用户同工具免审，跨会话失效；
   - `always`：该用户该工具永久免审，可随时撤销。
2. **判定在审批门（func 层）**：命中 active 授权 → 当轮直接执行（经统一脱敏管道）+
   台账记录；未命中 → 创建 pending（既有链路不变）。授权查询每次实时读库——
   撤销即刻生效，不做缓存。
3. **免审 ≠ 免记录**：授权执行也写 `ApprovalRequest`（status=executed、
   `grant_id`、`reviewed_by="grant:{scope}#{id}"`）——审计链完整，admin 队列可区分
   人审与授权执行。
4. **治理边界（与红线 #5 的关系是补充而非放松）**：授权只跳过 **HITL 人审**，
   不跳过权限矩阵——工具可见性仍由能力集白名单在 graph 构建时决定；执行后
   权限复查、脱敏、审计与正常调用完全一致。
5. **admin 控制**：`approve` 带 `grant_scope`（session 档要求请求有会话上下文，
   REST 单轮无会话 → 400）；幂等 upsert（同 user+tool+scope+conversation 的
   active 授权只刷新不堆叠）；`GET /approvals/grants` 台账 +
   `POST /approvals/grants/{id}/revoke` 软删撤销（409 防重复），全程 `_audit_admin`。
6. **可观测**：`bycall_approval_grant_bypass_total{scope}` 计数免审执行次数，
   并入 `ops-metrics` 人工接管维度（授权免审是接管率下降的合规来源）。

## 备选方案

| 方案 | 结论 |
|------|------|
| 提示词层声明「该用户可免审」 | 拒绝：策略绝不能活在提示词层（核心原则）；LLM 可被注入篡改 |
| RoleConfig 加 `approval_exempt_tools` | 拒绝：授权主体是「用户 × 工具 × 会话边界」三元的运营决策，塞进角色配置会混淆权限矩阵（能不能用）与人审策略（要不要人批）两件事 |
| 授权结果缓存（进程内 TTL） | 拒绝：撤销要等缓存过期才生效，违背「撤销即恢复人审」的安全预期 |
| session 档绑定 im_user_id 而非 conversation | 拒绝：同一 IM 身份多会话并存（红线 #2），会话才是审批发生的边界 |

## 后果

- **正**：高频可信操作的人审噪声显著下降（接管率可见改善）；授权全生命周期
  （授予/使用/撤销）落库可审计；三条新安全用例（会话边界/用户边界/撤销失效）
  进 T2.2 红线集，越权面被用例锁定。
- **负/边界**：授权查询给每次破坏性调用增加一次轻量索引读（user+tool+status，
  数据量极小，可忽略）；`always` 档被滥用的风险由控制面 UX 缓解（默认 once、
  档位说明内联、授权台账可随时撤销）。
- **风险**：管理员误选 always——缓解：台账页显著展示生效中授权 + 一键撤销；
  后续若需要，可加「always 档定期复审」提醒（不在本决策范围）。
