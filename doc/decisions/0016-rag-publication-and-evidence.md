# ADR-0016：RAG 索引发布与证据链修复

- **状态**：✅ 已采纳（批次 1–3 已落地，2026-10-15 完成回归验证）
- **日期**：2026-10-13
- **关联**：T1.1、T1.9、T2.1、T3.2；ADR-0001、ADR-0005

## 背景

部分 embedding/写入失败仍会留下可搜索 chunk；ACL 更新失败只回滚 SQL。
父块查询丢失元数据且未继承 ACL；跨不相交 KB 的 RRF 把排名当相关性；
查询改写与重排未接入执行链；检索故障等同无命中；引用来自预算前候选。

## 决策

1. 每次入库使用独立 generation doc_id。全部向量校验、写入与 flush 成功后，
   在同一个 SQL 事务中提交有效 generation、文档终态和统计。
   发布登记复用 SystemSetting 的内部 `_rag.index.<doc_id>` key，管理设置 API 不可修改。
   无需数据库或旧 zvec schema 迁移。检索前用 SQL 当前文档 ACL 和有效 generation
   构造 doc_id 白名单；空白名单不检索。无登记的旧文档仅 completed 可读。
   失败 generation 永不发布；旧向量清理失败仅留不可检索垃圾，不影响授权。
2. 父块只在子块所属 KB 内按精确 ID 查询，并继承 ACL 与有效 generation 过滤。
   zvec 的 fetch 不支持 filter，因此先精确读取授权元数据（不取正文），
   通过 ACL 与有效代检查后才精确读取父块正文。
   普通召回只搜索 child；保留 KB、文档、chunk、父块等来源信息。
3. 扩大每库候选池后，用已配置 reranker 对统一候选集排序；无 reranker 时明确
   采用统一候选上的关键词 BM25 降级模式（中文双字切分，无关键词交集则不注入）。KB 内 RRF 不作为绝对相关性或置信度。
   多轮查询在检索前依据同会话近期历史改写，失败回退原问题，ACL 独立计算。
4. 结构化记录 no-hit、失败与降级；引用只来自最终实际注入的证据与截断片段。
   离线回归覆盖失败索引、父子块 ACL、多库竞争、无答案与引用预算。

## 备选方案

仅异常后删除新 chunk 无法覆盖清理失败或进程中断；向量与 SQL 没有跨库事务。
新建 generation 表更规整，但增加部署迁移；当前复用内部 key-value 表，以后规模
增长时可迁移为专用登记表而保持检索契约。

## 后果

当前单进程嵌入式 zvec 写锁边界不变。失败重建会进入 failed 并暂时隐藏该文档；
ACL 更新失败恢复旧 ACL 与旧已发布状态。成功发布后尽力清理旧代；中断留下的
垃圾不进入检索。上线前已有 failed/processing 文档需管理员重新入库，不能推断
其中旧向量是否完整。登记查询与 doc_id 白名单随文档数量增长，后续需容量验证。
