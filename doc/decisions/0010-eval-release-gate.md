# ADR-0010：评测与发布门——离线四类评测集 + 灰度发布/一键回滚

- **状态**：✅ 已采纳
- **日期**：2026-08-15
- **背景**：战略诊断问题 #5——治理系统缺少自身评测/回放/发布门，无法自动证明「不越权、不回退」。阶段 1 已收口六条治理缝隙，但每次修改 prompt/Skill/模型/检索配置仍只能靠人工读代码判断风险，发布动作与质量证据脱节。
- **关联**：`doc/execution-plan.md` 阶段 2（T2.1–T2.5）、ADR-0004（version + is_active 模式）、ADR-0005（策略引擎）。

## 背景

Bycall 的卖点是「组织授权下的可靠执行」，但可靠执行不能靠宣言，必须可复现地验证：
1. 修改系统提示词 / 角色白名单 / 模型后，如何知道没有引入越权或质量回退？
2. 发布失败后，如何在数秒内退回上一个已知良好版本？
3. 评测若依赖真实 LLM 或外部服务，就无法进入 CI，也无法离线复现。

## 决策

1. **评测引擎与用例内置为 `src/bycall/evals/`**，四类评测集（知识质量 / 权限安全 /
   执行质量 / 运营效果）共享同一 runner；仓库根目录 `evals/` 只放 CLI 薄壳与说明。
2. **内置用例默认离线可跑**：真实 zvec（嵌入式）+ 隔离 SQLite + 局部打桩，不依赖真实
   LLM。权限安全用例覆盖五类攻击（越权召回 / 跨用户记忆泄漏 / 提示词注入 / 工具越权 /
   审批绕过），每类 ≥3 条，**任一失败即红灯**。
3. **`make ci-local` 纳入 `eval` + `eval-security`**：CI 与本地模拟同口径。
4. **离线回放 = 配置快照指纹 diff + 按变更类型选评测子集**：快照只存 SHA-256 与配置
   结构，不存提示词正文/密钥；`python -m evals.run --compare old.json new.json`
   输出配置 diff、旧/新两份报告与「是否越权/回退」判定，任一新配置用例失败退出码 1。
5. **发布门在控制面强制**：`POST /api/admin/prompts/{version}/publish` 与
   `POST /api/admin/models/{id}/publish` 先跑门（全量安全用例 + 相关质量用例），
   一个失败用例即 409，且不改任何 `is_active`。
6. **灰度 + 回滚复用现有 version + is_active 模式**：新增 `ReleaseState` 表记录
   （kind/target/previous/canary_percent/status/gate_report）。灰度比例 ∈ (0,100)
   时**不切 is_active**，运行时按 scope 稳定哈希（MD5 前 8 位 % 100）在代码层分流；
   `promote` 转全量，`rollback` 把 is_active 原子切回 previous。
7. **五维运营指标复用 Prometheus**：延迟（turn histogram）、成本（token 用量 × DB
   可调单价估算）、人工接管（HITL 审批事件）、失败（turn error）、重复执行（幂等拦截），
   控制面经 `GET /api/admin/ops-metrics` 展示同一 registry 快照，不另造埋点。

## 备选方案

| 方案 | 结论 |
|------|------|
| 引 Dify/DeepEval/Langfuse 等评测产品 | 拒绝：多一套外部服务与数据口径；当前四类评测的重点是治理红线（代码级可判定），自研 31 条离线用例已覆盖，接真实 LLM 评分时再扩展 runner 即可 |
| 全量评测进入 pytest | 拒绝：评测是独立出口门，需要 `make eval` 一条命令 + 发布门复用；但 runner 本身由 pytest 锁定行为 |
| 灰度用随机分流 | 拒绝：同一会话/用户会跳变、不可复现；稳定哈希分流可解释、可测试 |
| 为灰度新建「候选激活」字段挂在 SystemPrompt/Model 上 | 拒绝：把发布生命周期混入版本资产本身；独立 `ReleaseState` 单行 per kind 更清晰且审计集中 |

## 后果

- **正**：一条命令回答「这次改 prompt 有没有造成越权或质量回退」；CI 红灯与生产发布
  门口径一致；失败发布零副作用；回滚是秒级 is_active 切换。
- **负/边界**：内置用例是治理机制的离线校验，不替代真实业务语料的 LLM-as-judge 评分
  （试点阶段 T3.2 需按试点配置扩充用例）；`ReleaseState` 单行 per kind 意味着同时只能
  存在一个进行中的 prompt / model 灰度，符合当前单组织部署形态。
- **风险**：发布门跑 18 条安全用例会增加发布端点延迟（当前约百毫秒级，可接受）；
  若未来评测集接入 LLM，发布门应改为异步任务 + 轮询结果，不在请求内阻塞。

## 修订记录

- **2026-09-23（补齐控制面入口 + fail-closed，不改决策）**：T2.4 交付时只做了后端与
  「发布与回滚」展示页，控制台**没有任何发起发布的入口**（`publishPrompt`/`publishModel`
  无视图调用），而提示词「新建版本」、模型「激活」走的是不过门、也不写 `ReleaseState`
  的直接激活端点——发布页因此恒空、`promote`/`rollback` 恒不可达，决策第 5 条「发布门在
  控制面强制」在控制台实际不成立。现补齐发布入口（`PublishDialog.vue`：「发布与回滚」页
  「发起发布」+ 资产页行内「发布」，默认跑门并回显失败用例），并让控制台的提示词/chat
  模型生效**只能经发布门**（新建为候选版本、行内回滚到此改为发布该版本；向量/重排模型
  无发布门，仍用 `/activate`）。同时把决策第 6 条的回滚语义收紧为 **fail-closed**：
  `activate_target`/`activate_previous` 先解析目标再动 `is_active`，目标不可解析
  （版本/模型已删、或首次发布无上一版本）即 409 且 `is_active` 保持原状——此前的
  「先全部置 False 再激活目标」会静默清空生效配置（空系统提示词 / 无 chat 模型可用）。
