# Bycall 产品战略判断与后续方向

> 状态：建议稿（执行进度以 `doc/execution-plan.md` 为准） · 2026-07-30 初稿 · 2026-09-11 修订：按 ADR-0009 去商业化与去行业化——移除行业优先级与商务推进类内容，保留技术策略主线 · 关联：[决策登记册](decisions/README.md)（§8 决策点状态见其 §3）
> 范围：基于 v0.2.0 / M6 当前实现，记录 Bycall 的产品定位判断、能力缺口和后续路线（场景无关，ADR-0009）。  
> 约束：本文不替代 `product-design.md` 与 `architecture.md`；建议经评审后再拆入正式里程碑和 ADR。

## 1. 核心判断

Bycall 不应演化成另一个通用 Agent 搭建平台，也不应把核心价值归因于 RAG、LangGraph 或
MCP 本身。更合适的定位是：

> **企业数字员工的治理与执行平台**——数字员工不仅能回答问题，还能在组织授权、审批、
> 审计和数据边界内完成工作。

当前最有差异化的资产，是已经形成闭环的治理链：

```text
可信身份 → 当前能力集 → 知识预过滤 → 工具白名单
        → 人工审批 → 受控执行 → 结果脱敏 → 全程审计
```

这条链应当继续作为产品和架构的主轴。未来新增模型、渠道、工具、工作流或场景能力时，
都必须先进入治理脊柱，再向数据面放行。

定位表述用「企业级数字员工治理与执行平台」或「组织授权下的数字员工平台」，而不是
「企业知识库助手」——后者只能描述 Bycall 当前能力的一部分。

## 2. 当前能力判断

v0.2.0 已经是一个扎实的企业级落地底座，但还不是能直接承载复杂组织生产运行的成熟平台。

| 维度 | 当前判断 |
|------|----------|
| 企业问答 | 多知识库、混合检索、解析引擎、引用、多轮会话已形成较完整链路 |
| 组织治理 | 已有邀请制身份、RBAC、提示词/Skill 分发、工具白名单、审批和审计 |
| 执行能力 | MCP + capability token + HITL 已打通，具备从“回答”转向“办事”的基础 |
| IM 交付 | 企微已具备流式回复、主动推送、附件、引用卡片、模板卡片和可靠重连 |
| 多租户 | 实质仍是单组织模型，核心实体和会话键尚未形成完整租户隔离 |
| ABAC | 数据结构已有预留，实际 RAG 权限主要是 `source IN tags` 的角色标签过滤 |
| 工具结果治理 | 支持工具自带 redactor，MCP 可接收 capability meta；尚无统一的行列级结果策略 |
| 模型路由 | `Conversation.model_id` 已预留，运行时仍主要使用全局激活模型 |
| 生产治理 | M5 只完成部分可观测能力；SSO、合规报表、评测、灾备和迁移准备仍需补齐 |
| 任务执行 | 当前是单次对话内工具循环，尚不是持久化、可恢复的业务任务系统 |

因此，短期目标不应是增加更多“看起来聪明”的 Agent 能力，而应把现有治理能力变成
**可验证、可运营、可恢复、可复制**的企业产品能力。

## 3. 需要优先收口的实现缝隙

以下问题不会否定当前架构，但会限制 Bycall 进入真实企业生产环境：

1. **完整 ABAC 尚未闭环。** `ACLMetadata` 已预留 `tenant_id/dept/level` 等字段，当前
   检索入口实际主要把 `knowledge_scope_tags` 翻译为 `source IN (...)`。后续需要由统一
   policy 将用户属性、资源属性和上下文翻译成召回前过滤条件。
2. **会话键仍是单组织落地。** 文档红线定义
   `(agent_id, channel, tenant_id, user_id)`，当前 DB 形态主要是 `(user_id, channel)`。
   多租户、同租户多 Agent 和组织合并场景需要显式隔离键。
3. **模型绑定尚未生效。** `Conversation.model_id` 是正确的预留，但运行时仍取全局激活
   chat 模型。正式启用时需要把模型选择纳入能力集、成本策略和数据驻留策略。
4. **知识库可见范围语义需要统一。** `CapabilitySet.visible_kb_ids` 已计算，而数据面 runner
   仍遍历全部 KB。若该字段代表数据面 ACL，应接入检索；若仅代表控制面管理范围，应更名或
   移出能力集，避免把未生效字段误认为安全边界。
5. **工具结果策略需要平台化。** 目前结果脱敏依赖单个工具声明 redactor，MCP server
   主要靠 capability meta 自行鉴权。后续应支持统一字段分级、行级过滤、输出大小限制和
   审计脱敏策略，且默认拒绝未声明的数据类型。
6. **同步与流式治理链需收敛。** `run_agent` 与 `run_agent_stream` 有两套高度相似流程。
   策略增多后容易产生行为漂移，应抽出共享的策略准备、执行后处理和审计管线。

这些项目属于“治理承诺与实际执行保持一致”的工作，优先级高于增加新 Agent 花样。

## 4. 建议的能力演进主线

建议按以下顺序演进：

```text
可信问答 → 受控工具执行 → 可恢复的业务任务 → 参考流程包 → 跨系统数字员工
```

### 4.1 先完成 M5：企业生产化收口

M6 已完成，而 M5 仍是部分完成状态。按“治理先决、能力增强”的路线原则，下一步应先补齐：

- 企业身份：OIDC/SAML SSO、组织架构同步、离职即时撤权；有真实需求后再接 SCIM。
- 真正多租户：用户、角色、知识库、文档、会话、记忆、审批、审计、MCP 和缓存显式隔离。
- 完整 ABAC：部门、职级、项目、地域、密级和资源归属共同产生检索与工具策略。
- 管理职责分离：平台管理员、知识管理员、审批员、审计员不能默认共享全能权限。
- 合规审计：保留周期、字段脱敏、加密、访问审计、导出和不可篡改归档。
- 生产运维：数据库迁移、备份恢复、升级回滚、容量基线和故障演练。

控制面应新增“策略模拟器”：管理员选择用户、资源、动作和上下文，系统展示最终允许/拒绝、
命中的规则、能力集和过滤条件。这样治理不再只是代码属性，而是管理员可理解和验证的产品。

### 4.2 建立 Agent 评测与发布系统

企业 Agent 不能只证明“可以配置”，还必须证明变更没有造成质量回退或权限泄漏。

评测应覆盖四类指标：

- 知识质量：正确率、引用覆盖率、引用支持度、过期知识命中率。
- 权限安全：越权召回、跨用户记忆泄漏、提示词注入、工具越权、审批绕过。
- 执行质量：工具选择、参数正确率、任务成功率、重复执行率。
- 运营效果：延迟、成本、人工接管率、失败率和重复执行率（对齐 T2.5 五维指标）。

提示词、Skill、模型、检索配置和 MCP 工具变更应支持离线回放、新旧对比、安全门禁、灰度、
发布和一键回滚。场景包的评测数据应当和配置一同提交评测门，而不是部署后再临时补测试。

### 4.3 从工具循环升级为持久化任务系统

在现有 HITL 基础上引入 `Task / Step / Run` 等持久化实体，使数字员工能够处理分钟级、
小时级和跨天任务：

- 支持 IM 指令、定时器和业务事件触发。
- 每一步使用确定性状态机，具备幂等键、超时、重试和补偿。
- 支持中途审批、条件分支、人工接管、取消和恢复。
- 长任务进度和最终结果通过 IM 主动推送。
- 每次执行前重新计算能力集，避免任务创建后权限变化仍继续执行。
- 保留完整输入、决策、工具调用、审批和输出轨迹。

LLM 可以提出计划，但是否执行、如何重试、是否审批和如何补偿必须由代码层工作流决定。
在此之前，不优先建设多 Agent 自主协作或自由讨论式“Agent 群”。

### 4.4 建设连接器与参考场景包

MCP 解决协议问题，采用者真正需要的是现成接入和可度量的执行结果。连接器分为：

- **知识连接器**：企业网盘、SharePoint、Confluence、飞书/企微文档、邮件、数据库。
- **业务连接器**：ERP、CRM、MES、WMS、ITSM、HR、OA、合同和财务系统。

知识同步不能只复制正文，还要同步外部文档 ID、版本、原系统 ACL、删除/撤权事件、更新时间，
并暴露权限漂移与同步失败告警。

一个完整的场景包应由以下资产组成：

```text
角色 + 提示词 + Skill + 知识库结构 + 连接器 + MCP 工具
     + 审批策略 + 评测集 + 运营看板
```

场景包支持整体复制与改造（ADR-0009：垂直场景由采用者自定义），是平台能力复用的关键单位。

## 5. 场景定位（行业无关，ADR-0009）

平台不锁定行业、不维护行业优先级（ADR-0009，2026-08-15）：垂直场景由采用者基于平台
治理能力自行组装，行业词汇不进平台核心。仓库交付两类参考资产：

- **参考场景包**：`examples/connectors/` 两个示例 MCP 连接器（demo 工单/库存）
  + 3 类示例角色（一线/主管/访客）+ demo 账号，`make seed-reference` 幂等灌入；
- **平台级参考流程**：查询-创建闭环 / 高危 HITL 回推 / 多轮上下文与能力边界
  （T3.2，见 `doc/specs/t3.2-platform-flows.md`）。

具体的行业应用方向由采用者自行选择与实现，不进入平台路线图与核心词汇。

## 6. 建议的 90 天验证计划

> 历史建议稿；实际执行进度见 `doc/execution-plan.md` 阶段 0–3。

### 第 1 月：企业化收口

- 明确租户与组织模型。
- 接入企业 SSO 和人员撤权。
- 完成 ABAC 过滤闭环。
- 补齐审计留存、脱敏和策略模拟器。

### 第 2 月：可信发布

- 建立平台评测集和权限攻击用例。
- 支持 Prompt/Skill/模型版本回放。
- 建立发布门、灰度和回滚机制。

### 第 3 月：参考场景与平台级流程

- 落地 3 类角色、2 个示例连接器、3 条端到端流程和 1 条高风险审批链（对应 T3.1–T3.3）。
- 基于 T2.5 五维指标建立使用看板（延迟、成本、人工接管率、失败率、重复执行率）。

建议验收指标至少包含：未授权召回为零、引用覆盖率、工具参数正确率、任务成功率、重复执行率、
人工接管率、平均处理时间下降，以及审批与执行能否完整追溯。具体目标值应由真实使用基线决定，
不在平台层预设脱离实际的统一数字。

## 7. 暂不优先的方向

在生产治理、评测和任务系统完成前，暂不优先建设：

- 通用低代码 Agent 画布。
- 多 Agent 自由协作或“Agent 群聊”。
- 插件/Skill 公共市场。
- 数字人形象、虚拟主播和大规模语音交互。
- 员工自行修改系统提示词或能力边界。

这些功能展示性强，但会稀释 Bycall 当前最有价值的“组织授权下的可靠执行”。只有当它们能
复用同一治理脊柱、通过安全评测并服务明确的组织业务结果时，才应进入正式路线图。
